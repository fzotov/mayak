Дата подготовки: 14 ноября 2026 года.
Назначение: входные данные для Claude Code при дополнении технического задания существующей системы.

## 3. Объем интеграции

**Подтверждено [S1, S5–S9]:** Sber API поддерживает получение операций по корпоративным счетам, дневных остатков/оборотов, изменений выписки и файлов для экспорта. По сценарию «Компаниям» перечислены расчетные, транзитные и депозитные счета; применимость конкретного метода к типу счета необходимо сверить с его схемой.

**Проектное требование:** первый этап — доступ на чтение. Создание платежных поручений и подписание платежей не входят в объем. Реализовать:

1. Подключение организации и выбор доступных счетов.
2. Первичную загрузку истории за выбранный период.
3. Регулярное получение новых и измененных операций.
4. Дневные остатки и обороты для сверки.
5. Загрузку исходных файлов выписок.
6. Повторную синхронизацию без дублей, журнал ошибок и мониторинг подключения.

## 4. Подключение организации

**Подтверждено [S2, S11]:** подключение выполняется через СберБизнес: «Все продукты и услуги» → «Сбербанк API» → «Sber API» → «Подключить». Далее выбираются наборы API, создается и подписывается заявление. Возможность подписи зависит от полномочий пользователя/доверенности. В кабинете доступны параметры сервиса, в том числе client_id, управление client_secret и Redirect URI. Для разработчиков предусмотрена роль «Разработчик Sber API».

**Проектное требование:** подготовить инструкцию администратору организации. Параметры доступа получать через предусмотренный банком процесс; не запрашивать пароль интернет-банка внутри нашей системы.

**Требует проверки:** точное наименование набора и состав прав для собственной компании, возможность работы с несколькими собственными организациями, тариф и порядок оплаты. Не считать API бесплатным без проверки условий.

## 5. Авторизация и срок действия ключей

**Подтверждено [S1, S4]:** используется СберБизнес ID. Общий сценарий: авторизация пользователя → получение authorization code → обмен на access_token/refresh_token → обращения к API → обновление токенов через `POST /v2/oauth/token`.

| Параметр | Значение из документации |
| --- | --- |
| Authorization code | Одноразовый; срок жизни 2 минуты |
| Access token, полученный через API | 60 минут |
| Токен из личного кабинета | 30 дней; после обновления через API действует стандартный срок 60 минут |
| Refresh token | 180 дней с последнего успешного использования; обновление возвращает новую пару токенов |
| Client secret | Срок действия 40 дней; обновление через `/v1/change-client-secret` или кабинет [S2] |

Однократная начальная авторизация и последующее автоматическое обновление позволяют работать без ручного входа для каждой выгрузки. Это не гарантия бессрочного доступа: система должна обрабатывать отзыв разрешений и необходимость повторного подключения.

**Проектные требования:** обменивать code сразу в серверном callback; проверять state; хранить секреты зашифрованно; сохранять новую пару токенов атомарно; исключить конкурентное обновление одной пары; запускать обновление заранее; после 401 разрешать один цикл обновления с повтором исходного запроса. При invalid_grant/отзыве доступа переводить подключение в состояние повторной авторизации. Настроить ротацию client_secret с запасом до истечения срока.

**Требует проверки:** точные URL OAuth, HTTP-метод и контракт ротации client_secret, обязательные scopes, формат Authorization, поддержка PKCE, правила отзыва и перехода между старыми/новыми секретами. Не добавлять Bearer автоматически без проверки схемы банка.

## 6. TLS и окружения

**Подтверждено [S3]:** Sber API использует mTLS. Нужен клиентский сертификат, например контейнер PKCS#12 `.p12`, и доверенная цепочка удостоверяющих центров Сбера/Минцифры. Сертификат привязан к конкретному client_id; срок действия — 12 месяцев. Тестовый сертификат действует только в тестовом окружении. Промышленный сертификат можно сформировать через кабинет либо получить через поддержку по CSR.

**Проектное требование:** выделить настройки sandbox/production; хранить сертификат и закрытый ключ на сервере; проверять серверный сертификат; не отключать TLS verification; отслеживать срок сертификата и давать уведомления о перевыпуске.

**Требует проверки:** действующие base URL, порты и пути API для каждого окружения, доступность из выбранной инфраструктуры, требования к исходящим IP и сетевым разрешениям. Использовать адреса из актуальных параметров сервиса и документации; не копировать окружения из старых примеров v1.

## 7. Методы API

Пути ниже относительные. Base URL и общий префикс определяются окружением банка.

| Назначение | Метод и путь | Параметры / замечания | Источник |
| --- | --- | --- | --- |
| Сведения о пользователе и доступных счетах | `GET /v2/oauth/user-info` | В сценарии указан scope `openid`; схему перечня счетов проверить | S1 |
| Обновление токенов | `POST /v2/oauth/token` | Проверить grant_type, обязательные поля и Content-Type | S1, S4 |
| Операции по счету за дату | `GET /v2/statement/transactions` | `accountNumber`, `statementDate`, `page`; scope `GET_STATEMENT_ACCOUNT` | S6 |
| Остатки и обороты за день | `GET /v2/statement/summary` | `accountNumber`, `statementDate`; scope `GET_STATEMENT_ACCOUNT` | S7 |
| Изменения/интервал внутри дня | `GET /v2/statement/increment` | Счет, временные фильтры; полную модель и пагинацию проверить | S8 |
| Данные конкретной операции | `GET /v2/statement/transactionId` | `accountNumber`, `statementDate`, `operationId`; scopes `GET_STATEMENT_ACCOUNT`, `GET_STATEMENT_TRANSACTION` | S5, S10 |
| Запустить формирование файла | `GET /v1/statement/files` | `accountNumber`, `statementDate`, `encoding`, `format`; scope `GET_STATEMENT_ACCOUNT` | S9 |
| Получить результат задачи/ссылку | `GET /v1/statement/tasks-for-download/{taskId}` | taskId из результата формирования | S5, S9 |
| Скачать файл | `GET /v1/statement/download/{fileId}` | Следовать контракту результата задачи | S5 |
| Печатная выписка | `GET /v1/statement/print` | Опционально; параметры уточнить в соответствующем разделе S5 | S5 |

Сочетание v1 для файлов и v2 для операций присутствует в действующем справочнике. Не заменять версии механически.

### 7.1. Операции за дату

**Подтверждено [S6]:** доступна выписка по рублевому или валютному счету за выбранную дату. Access token передается в заголовке Authorization. Данные запрашиваются постранично, начиная с `page=1`. Доступная история — предыдущие 5 лет и текущий год.

**Проектное требование:** диапазон дат обрабатывать как набор дневных запросов. Не считать первую страницу полной выпиской. Признак последней страницы и размер страницы взять из актуальной схемы, не фиксировать историческое значение «100» без проверки. Не превращать ошибки валидации/доступа в пустую выписку.

### 7.2. Остатки и обороты

**Подтверждено [S7]:** summary возвращает входящий/исходящий остаток и суммарные обороты по счету за один день; принимает счет, дату и токен доступа.

**Проектное требование:** хранить дневную сводку отдельно от операций. Выполнять сверку в валюте счета с учетом банковской семантики дебета/кредита. Расхождения фиксировать как отдельное состояние, не исправлять банковские значения автоматически.

### 7.3. Инкрементальное получение

**Подтверждено [S8]:** ресурс возвращает операции и измененные записи. Документация описывает `statementDate`, `lastModifyDate`, `lastModifyDateTo`. Нельзя одновременно передавать `statementDate` и `lastModifyDate`; `lastModifyDateTo` используется совместно с `lastModifyDate`. Для временных отметок приводится формат `YYYY-MM-DDThh:mm:ss[.SSS]`.

**Проектное требование:** хранить checkpoint отдельно по каждому счету. Продвигать его только после успешного сохранения всех страниц. При повторе допускать пересечение интервалов и обновлять существующие записи. Дополнительно выполнять дневную сверку для обнаружения корректировок.

**Требует проверки:** timezone банковских временных отметок, включительность границ, переход через операционный день, семантика reloadTime и фильтрации прошлых дат. Описание и примеры ресурса содержат нюансы, поэтому нельзя строить обработку только по названию метода.

### 7.4. Файлы выписок

**Подтверждено [S9]:** запрос формирования возвращает идентификатор задачи `id`. Дальнейшее получение ссылки выполняется через ресурс tasks-for-download. При запросе задаются счет, дата, кодировка и формат. Документация отдельно требует соблюдать порядок параметров модели запроса.

**Проектное требование:** реализовать асинхронный цикл «создание → ожидание результата → скачивание → сохранение». Ограничить время ожидания и число повторов. Хранить метаданные файла: организация, счет, дата, формат, кодировка, размер, checksum, время загрузки, статус. Исключить повторное архивирование идентичного файла.

**Требует проверки:** допустимые значения `format` и `encoding`, конкретные статусы задачи, срок действия ссылки, срок хранения результата, поддержка периода/только дня. Не обещать CSV/XLSX/1C/PDF для данного метода до проверки enum; печатный экспорт — отдельный ресурс.

## 8. Лимиты и ошибки

**Подтверждено [S5]:** для перечисленных в справочнике методов выписок указана пропускная способность 5 TPS. Область действия лимита необходимо уточнить; не считать его автоматически независимым для каждого счета.

**Подтверждено [S4, S9]:** в API могут встречаться 401, 403, 429, 5xx; FAQ объясняет `202 STATEMENT_RESPONSE_PROCESSING` как формирование/актуализацию выписки. Точный набор кодов зависит от ресурса.

**Проектная политика обработки:**

| Ситуация | Действие системы |
| --- | --- |
| 401 | Одно контролируемое обновление токена и повтор; далее запрос повторного подключения |
| 403 / нет разрешения на счет | Показать проблему прав; остановить бессмысленные повторы |
| 429 | Уменьшить частоту; Retry-After учитывать, если он возвращается |
| Timeout / временный 5xx | Ограниченные повторы с экспоненциальной задержкой и jitter |
| 202 processing | Продолжить ожидание по контракту ресурса; не считать результат пустой выпиской |
| Ошибка параметров/даты | Исправление параметров; без бесконечных повторов |
| Нет данных | Отличать подтвержденное отсутствие операций от ошибки получения выписки |

Все запросы выполнять через общий настраиваемый rate limiter, начально с консервативной частотой ниже 5 TPS. Статусы и ошибки журналировать без токенов, паролей и закрытых ключей.

## 9. Предлагаемая модель хранения — проектное решение

Названия ниже являются внутренними сущностями нашей системы, не полями ответа Сбера.

| Сущность | Основные данные |
| --- | --- |
| BankConnection | Организация, окружение, client_id, ссылки на секреты, scopes, статус доступа, сроки ключей |
| BankAccount | Организация, номер счета как строка, валюта, доступность, дата последнего обновления |
| BankTransaction | Идентификатор банка, счет, дата выписки, сумма/валюта, направление, контрагенты, назначение и статус при наличии в API |
| DailyStatementSummary | Счет, дата, остатки, обороты, результат сверки |
| StatementFile | Счет, дата, формат, кодировка, checksum, ссылка на защищенное хранилище |
| SyncCheckpoint | Счет, завершенный период/курсор, время последнего успеха |
| SyncRun | Период, страницы/число записей, итог, код ошибки, время выполнения |

Денежные значения хранить с точной десятичной арифметикой. Правила уникальности операции определить после проверки стабильности operationId: ключ должен включать как минимум контекст организации и счета. Полный ответ банка, если сохраняется, размещать в защищенном хранилище с политикой доступа и сроком хранения. Не отождествлять отсутствие поля с нулевым значением.

## 10. Настройки интеграции — проектное решение

Предусмотреть конфигурацию: окружение; base URL; client_id; ссылки на client_secret, TLS-сертификат/ключ и пароль контейнера; Redirect URI; подтвержденные scopes; разрешенные организации/счета; глубина первоначальной истории; расписание опроса; timezone; лимит запросов; timeouts; число повторов; интервал опроса файлов; срок хранения данных.

Рекомендуемый стартовый режим: настраиваемый опрос раз в 15 минут и ежедневная сверка предыдущего дня. Это наше предложение, а не гарантия скорости обновления данных банка. Конкретное расписание и глубину истории включить в настройки проекта.

Секреты, токены и сертификаты не включать в ТЗ, репозиторий, браузерный код и примеры логов. Примеры должны содержать placeholders.

## 11. Критерии приемки

- После подключения система показывает только доступные организации и счета.
- Первичная загрузка обрабатывает несколько дней и все страницы выписки.
- Повторная загрузка одного дня не создает дубли; изменения обновляют существующие записи.
- После сбоя checkpoint сохраняет возможность безопасно продолжить синхронизацию.
- Истекший access token обновляется автоматически; конкурентные задачи не теряют refresh token.
- Отзыв разрешения и истечение ключей приводят к понятному статусу и уведомлению.
- Дневные остатки и обороты сверяются; расхождения видны оператору.
- Файл выписки проходит весь цикл формирования и доступен уполномоченному пользователю.
- Проверены сценарии 401, 403, 429, timeout, 5xx, processing и пустой результат.
- Проверены денежная точность, валютные счета, границы дат/часовых поясов и изоляция организаций.
- В логах, исходниках и клиентском коде отсутствуют секреты.
- Sandbox-проверки и ограниченная промышленная сверка с выпиской СберБизнес документированы отдельно; mocks не считаются подтверждением работы с банком.
